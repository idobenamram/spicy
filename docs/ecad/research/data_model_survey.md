# How simulators and compilers lay out circuit data

> Research report, 2026-09-26. Six research agents each read one set of sources and answered the same questions with citations. Conclusions are merged into `../circuit.md`.
> Sources were read from cloned repositories in `/tmp/refs` (ngspice, Xyce, Gnucap, OpenVAF, VACASK, the MLIR docs, Cranelift, the rustc-dev-guide, rust-analyzer) and, where marked, from the web. Anything an agent couldn't verify is marked "not verified" or "inferred".

**The questions every simulator report answers:**
1. How a netlist becomes the simulator's structures.
2. Models vs instances: what's shared, and what's precomputed per model.
3. Where `m`, `area` and `scale` are applied.
4. Who allocates internal nodes and branch unknowns, and whether that depends on parameter values.
5. Where matrix positions are stored, and when they're rebuilt.
6. The order of unknowns and devices.
7. Where temperature-derived values live.
8. Where dynamic state (charges, history) lives.
9. What's recomputed when a parameter changes between runs.
10. How cross-device references (F/H sources, mutual inductors) are resolved.
11. Data layout, dispatch and parallelism.
12. Other lessons.

The compiler reports (MLIR; data-oriented compilers) answer their own lists, given in each section.

## MLIR

Sources key: D/ = /tmp/refs/llvm/mlir/docs/. S/ = llvm-project main, fetched 2026-09-26 from raw.githubusercontent.com. P = arXiv 2002.11054v2 (Lattner et al.). I read the RFC through a summarizing fetch, so treat its details as paraphrase. ngspice = /tmp/refs/ngspice.

### 1. Progressive lowering and dialects
- What MLIR does: it lowers in small steps. "The loss of structure is then conscious and happens only where the structure is no longer needed." "Attempts to raise semantics once lowered are fragile." Levels may be mixed in one IR.
- Citations: P §2 ("Progressive lowering", "Maintain higher-level semantics"); D/Rationale/RationaleLinalgDialect.md:462-495 ("Avoid Raising", "Don't Lose Information too Quickly"); partial conversion at D/DialectConversion.md:21-28.
- Lesson: Deck is the SPICE dialect. SPICE precedence, given-flags, .model inheritance and binning, `scale` and dialect defaults should all end inside lower(&Deck). What survives is whatever a later stage would otherwise have to rebuild. Two things qualify:
  - Model identity (which instances share a model). Rebuilding it from equal numbers would be raising, so keep a ModelId.
  - The path from a knob to a field. If m and area are folded into Params (pipeline.md Decision #7), a run that varies a .model IS must apply ·area·m again. Make the fold one function that both nominal lowering and Binding call. Don't apply it once to the numbers and throw away the formula.
  - Structure that depends on a value is decided at lowering and frozen. ngspice drops the diode's internal node when RS=0 (ngspice/src/spicelib/devices/dio/diosetup.c:390-401). If any run can move RS off 0, lowering must keep the node.

### 2. Uniquing and interning
- What MLIR does:
  - Attributes and types are value-typed handles to storage "uniqued within an instance of an MLIRContext". The storage is immutable and "immortal", looked up by KeyTy, hash and ==.
  - This buys equality by pointer compare, dedup and cheap copies.
  - Changing a value means building a new key, then re-hashing and re-uniquing it. The old value stays alive.
  - A "mutable component" is kept out of the key and is meant only for data that can't be set at construction.
  - "Transient scopes" let temporaries be freed.
- Citations: S/mlir/docs/DefiningDialects/AttributesAndTypes.md:38-42, 993-1004, 1014-1027, 1084-1090; S/mlir/include/mlir/IR/MLIRContext.h:41-43.
- Lesson:
  - Intern resolved .model cards at lowering into a per-kind model table. Identical cards get one ModelId. Equality is then an integer compare, grouping by model costs nothing, and a BSIM4 card is stored once: about 900 model entries against about 100 instance entries (ngspice/src/spicelib/devices/bsim4/b4.c:31-133 vs 134-1082).
  - ngspice already dedups derived data this way: its size-dependent params are keyed by (L, W, NF) (bsim4/b4temp.c:421-434).
  - Copy-on-write: when one instance overrides a model value, intern a new model entry. Never mutate the shared one.
  - Never intern per-run values. 10k Monte Carlo samples × per-instance overrides would grow the table without bound, which is MLIR's "leak" (§3). Per-instance mismatch belongs in instance fields (BSIM4 has instance `delvto` and `mulu0`, b4.c:56-58) or in per-run Params.

### 3. Inherent vs discardable attributes, and Properties
- What MLIR does:
  - Inherent attributes carry the op's semantics and the op verifies them. Discardable attributes are dialect-prefixed and defined outside the op.
  - Attributes are "constant data ... in places where a variable is never allowed". Values that vary at runtime are operands.
  - Properties are "extra data members stored directly on an Operation class": a fixed-size C++ object that lives in the Operation's allocation, not in the context.
  - Why Properties were added (RFC): each attribute setter copied the dictionary, edited it, re-hashed it and re-uniqued it. Every setter "leaked" a dictionary into the context permanently. Reads were string-key lookups, and lifetime was tied to the context.
  - The cost: equality is no longer a single pointer compare, and hashing needs a hook. The summary found no benchmark numbers in the RFC (not verified).
- Citations: D/LangRef.md:778-785, 796-797, 805-827; S/mlir/docs/DefiningDialects/Operations.md:180-182, 195-196; S/mlir/include/mlir/IR/Operation.h:75-79; RFC.
- Lesson: use three tiers.
  - Interned, immutable and shared: model cards and kind descriptors. These are the attributes/types tier.
  - Inline, typed, fixed layout, no names, no Option: Vec<BjtParams>. This is the Properties tier, and it backs Decision #4's typed Params copy over any dictionary.
  - Per-run values act as operands. They are inputs to the Plan and never baked into it.
  - Discardable metadata (names, origins, spans) goes in side tables that simulation never reads.

### 4. Operation memory layout
- What MLIR does:
  - An Operation is one heap allocation. Its results are placed before it in reverse order. Operands, properties, successors and regions trail it, and operands can move out of line.
  - Operations sit in intrusive lists inside Blocks, and Block size() is O(n).
  - Each result points to its first use. Uses form doubly linked lists so replace-all-uses (RAUW) is cheap.
- Citations: S/mlir/include/mlir/IR/Operation.h:40-88; D/Tutorials/UnderstandingTheIRStructure.md:77, 274-280.
- Lesson: this layout is built for insert, erase and RAUW during rewriting. It pays with a node per op and pointer chasing. That fits an editable top form such as Design, not Circuit or Plan. Keep dense u32 ids, per-kind parallel arrays, and precomputed matrix-position stamp arrays (pipeline.md §3). Where you need "devices per node", build a CSR adjacency once instead of use lists.

### 5. Symbols and symbol tables
- What MLIR does:
  - Cross-references use a non-SSA SymbolRefAttr, resolved by name in the nearest symbol table. A symbol may be used before it is defined and referenced across isolated regions.
  - This exists because if isolated ops could reach use-lists above them, IR updates would need "expensive locking". MLIR uses local constant pools plus symbols for globals instead, and "does not feature whole-module use-def chains".
  - Costs:
    - Lookup is a linear scan unless cached.
    - SymbolTableCollection builds its tables lazily, which makes reads "not thread-safe", so LockedSymbolTableCollection exists.
- Citations: D/SymbolsAndSymbolTables.md:5-25, 72-80, 123-146; P §4.3; S/mlir/include/mlir/IR/SymbolTable.h:282-285, 343-350, 509-511.
- Lesson:
  - In Deck and Design, keep references by name (`F1 ... Vsense`, `K1 L1 L2`; use-before-def is normal SPICE).
  - At lowering, resolve them to typed ids (VsrcId, InductorId) and check the kind. Names go to a side table.
  - Build any name→id map eagerly and completely, so it is Sync with no locks. Nothing lazy.
  - Ids into an immutable Arc<Circuit> give lock-free parallel runs, MLIR's own reason for symbols.

### 6. Pass manager and analyses
- What MLIR does:
  - Passes anchor on IsolatedFromAbove ops. They must not touch sibling ops and must hold no global mutable state. Each thread gets its own copy of a pass.
  - Analyses are computed lazily and cached. Every pass invalidates all analyses unless it marks them preserved, and an analysis can decide for itself with isInvalidated.
  - DataLayout caches its answers until the scope is modified, and asserts on that when assertions are enabled.
- Citations: D/PassManagement.md:24-51, 216-238, 301-323, 360-369; D/Rationale/Rationale.md:1052-1062; D/DataLayout.md:84-94.
- Lesson: when to recompute what.
  - Plan (node numbering, sparsity pattern, stamp positions, KLU symbolic analysis) depends only on wiring and device kinds. It survives parameter changes and is rebuilt only when wiring changes.
  - Derived depends on Params and Conditions and is rebuilt every run.
  - The numeric factorization is rebuilt every Newton step.
  - Give Plan a record of the Circuit it was built from (identity or generation number) and assert on it, as DataLayout does.
  - Collect the parameters that change structure (the RS==0 example in §1) into a key. A new Params that changes that key needs a new Plan. This is the isInvalidated analog.

### 7. Dialect conversion and legality
- What MLIR does:
  - A ConversionTarget marks ops Legal, Dynamic (legal only under a callback) or Illegal. Anything unmarked is "unknown".
  - Full conversion fails unless every op becomes legal. Partial conversion tolerates unknown ops. Analysis conversion only reports what could be legalized.
  - Patterns chain transitively: bar.add → baz.add → foo.add.
  - Rollback mode has "a significant toll on compilation time".
- Citations: D/DialectConversion.md:16-80, 156-165, 255-263.
- Lesson:
  - Define simulate-ready as a checked predicate, Circuit::verify: every kind is supported by this build (Dynamic legality, e.g. a MOSFET LEVEL or version, or an OSDI module that is loaded), every reference is a resolved id, every number is finite, there is no hierarchy, and ground exists.
  - Both front ends aim at it with full-conversion semantics and diagnostics.
  - A dry run listing unsupported devices is the analysis-conversion analog.
  - No rollback engine: lowering is a deterministic single pass.

### 8. Performance of the IR itself
- What MLIR does:
  - The uniquer is sharded (8 shards by default), with a reader/writer mutex per shard, a thread-local cache and a read-only fast path.
  - The context spawns a thread pool by default. That is "undesirable" for many contexts or long-lived processes, so an external pool can be injected.
  - LLVM couldn't parallelize because globally uniqued constants carry mutable use lists. MLIR's fix: immutable uniqued data, per-op constant pools, non-SSA globals, one pass copy per thread.
  - Bytecode: skippable length-prefixed sections, lazy attribute/type loading via an offset table, isolated regions in their own sections, custom encodings "significantly smaller and faster" than text.
- Citations: S/mlir/lib/Support/StorageUniquer.cpp:20-26, 69-82, 136-148, 160-178, 263; S/mlir/include/mlir/IR/MLIRContext.h:49-59, 202-211; D/Rationale/Rationale.md:1033-1065; D/BytecodeFormat.md:122-124, 211-215, 269-273, 373-376.
- Lesson:
  - No hashing, interning or locks on the per-run path.
  - Take the caller's rayon pool rather than creating one per Plan.
  - If PDK libraries or Plans are cached on disk, use an offset-indexed binary format so only the referenced models load.

### 9. Where MLIR is the wrong fit for our hot path
- Open-world genericity. Ops carry string names, attribute dictionaries and vtable-dispatched interfaces (D/LangRef.md:315-321; D/Interfaces.md:206-266). Our kinds are a closed set plus OSDI: use enums and per-kind Vecs, and dispatch OSDI once per kind batch, not once per device.
- A pointer graph with use lists (§4). The hot loop wants flat arrays.
- SSA values are directed, single-source multi-edges (D/LangRef.md:611-613). Circuit nets are undirected and symmetric across terminals, so nodes should be ids, not values. Dominance and regions have no role.
- Interning or locking per-run data (§2, §3, §8).
- Name lookup at run time (§5).
- A general rewrite driver with rollback, when we have a few fixed stages (§7).
- Mutation-first, no-const IR (D/Rationale/UsageOfConst.md:5-15), when we need an immutable, Sync, Arc-shared Plan plus per-thread Workspace.
- Copy instead: deliberate drops with no raising, immutable-shared plus per-thread-mutable state, isolation for parallelism, a verifiable legality target, and cached analyses with explicit invalidation.
